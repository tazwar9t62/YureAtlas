# Durable local scheduling

Automatic scheduling applies to real experiments. Synthetic demo work remains explicit. Schedule decisions are stored separately from worker heartbeat updates: a live worker does not prove that its scheduled decisions have been committed.

## Persisted settings and worker application

`GET /schedules` returns the requested configuration, the registered worker's process setting, the last committed application, and the currently applicable kinds. With no saved configuration, revision `0` represents the installation defaults: enabled, all real experiments, and all five job kinds. `PUT /schedules` appends an immutable revision with `expected_revision`, `spec`, and a reason of 1–500 characters. A stale expected revision returns HTTP 409; reload before saving again. `GET /schedules/history` returns newest revisions first, with a default page of 25, a maximum of 100, and a `before_revision` cursor. Editing settings never changes an earlier revision or job.

The specification supports `enabled`, `scope` (`all_real` or `selected`), `experiment_ids`, and `kinds` (`ingest`, `forecast`, `evaluate`, `reconcile`, `train`). Selected scope accepts at most 100 distinct existing real experiment IDs; all-real scope requires an empty ID list. Empty selected scope or an empty kind list is valid and creates no automatic work. Ingestion applies only to USGS experiments, so an ingestion-only JMA scope also has no applicable work. The regular JST times below are fixed in this version; these settings choose work and scope, not custom cron expressions.

The worker's `SCHEDULE_ENABLED=false` is a hard process-level disable. Persisted settings cannot override it. The status response exposes the API process setting separately: an enabled API does not establish that the worker is enabled. Worker status checks the registered singleton session and heartbeat; a missing, offline, stale, or clock-skewed worker cannot establish current application. When requested work is otherwise enabled but the worker's state is unverified, `effective_enabled` is `null`. A persisted disable or inapplicable scope can establish `false` without a live worker.

`last_application` identifies the revision, normalized specification hash, worker ownership token, and time of the last successfully committed planner pass. `application_status` distinguishes `current`, `pending`, `worker_unverified`, and `environment_disabled`. A saved revision is not itself a worker acknowledgment. A failed pass leaves the previous application record intact. These fields describe configuration application; the historical acknowledgment does not promise that the next job will finish or publish.

With the worker process enabled, the timer keeps polling even when persisted settings disable scheduling. A successful disabled or no-work pass acknowledges that configuration without advancing the decision cursor. An environment-disabled worker starts no scheduling timer and records its process setting during worker registration. Re-enabling the process or persisted policy resumes bounded recovery.

Configuration writes, schedule planning, and job claims serialize through the same advisory lock. Disabling settings, removing a kind, or removing an experiment pauses matching queued automatic work and expired attempts awaiting recovery. It preserves their payloads, pinned targets, status history, and logical keys. Manual work remains claimable. Already running attempts continue; stop them with explicit cancellation. Terminal cleanup can still mark cancelled or retry-exhausted queued/expired jobs as cancelled or failed while dispatch is paused, but it cannot restart them. Re-enabling a queued forecast does not move its pinned target; an expired unpublished target becomes missed when executed.

## Worker ownership and cancellation

One worker owns an idle autocommit PostgreSQL advisory-lock session and a registered ownership epoch. Its scheduler carries that same epoch. Every new claim records a fresh attempt token and the worker token; an expired attempt cannot renew its lease, mark successful completion or publish archive changes. The still-current attempt may finalize an acknowledged cancellation after expiry. Leases and heartbeats use the database wall clock. A replacement worker waits for the old lease to expire before reclaiming a running job; a job receives at most three total attempts. Claim scans inspect at most 100 queued or expired jobs per poll, finalizing cancelled or exhausted entries before considering later work.

Protected domain transactions flush their changes, then verify and hold the current worker and job rows through commit. This covers catalogue revisions, snapshots, fitted model references, forecasts and evaluations. The scheduler verifies its worker epoch before committing jobs and its decision state. A lost worker stops on its next ownership check. The singleton session is explicitly unlocked and physically discarded on exit; cleanup does not replace a primary execution failure.

Cancelling a queued job makes it terminal immediately. Cancelling a running job records a request; its next progress check or domain transaction boundary stops it. An individual bounded fitting or simulation call can continue computing until that boundary. A cancellation request that wins the job-row lock prevents subsequent publication and completion; a completion that commits first remains completed. Failed and cancelled jobs retain their last useful progress instead of displaying 100%. Earlier committed batches and immutable artifact bytes remain available, while uncommitted domain writes roll back. A cancelled or replaced attempt cannot overwrite a newer attempt's progress or result.

These boundaries serialize acknowledged cancellation and worker takeover with publication. They do not claim that an instantaneous physical connection loss can undo a transaction whose ownership check already succeeded; successor registration waits for that transaction to finish. Direct explicit CLI work outside the worker is not governed by a job cancellation token.

## Forecast request and retry identity

A new forecast job preserves its original request in `payload` and records its target in `execution` at enqueue time. An implicit manual target starts exactly 30 minutes after that request timestamp; an explicit target is normalized to UTC. The input cutoff is always 30 minutes before the target, and the window lasts 24 hours. Reusing the same logical job key returns the existing request and target unchanged. Waiting in the queue does not move a target forward.

Before publication, the current owned attempt resolves the experiment, model and selection provenance once. Selection uses an explicitly requested model, otherwise the latest promotion, otherwise the latest available historical-rate model. Automatic selection considers records created by the database's selection timestamp; creation time and ID provide deterministic ordering for ties. An incompatible promotion produces an explicit failure instead of silently selecting another model. The saved resolution records the selection policy, promotion identity/reason where applicable, model artifact and timing, and canonical forecast key. The database permits a pinned target to become fully resolved while retaining its original target fields; it rejects later changes to the resolved identity. Jobs expose both the original payload and execution record through the API.

A forecast job may publish only its complete saved resolution. A retry first looks for the exact immutable publication identified by that resolution. If publication succeeded before a crash but job completion did not, recovery returns that same forecast even after the deadline or a later promotion; it does not reload the model artifact just to return an existing archive. With no existing exact publication, an expired target produces a typed missed-deadline result before model selection or artifact access. Deadline classification uses an error type and structured reason, not words in a generic exception message. A delayed manual request can therefore become missed as well as a scheduled request.

Legacy jobs without an execution record require an explicit policy. A never-attempted legacy request derives its target from its explicit start or original creation time plus 30 minutes, then persists a successful resolution once. If an expired legacy target fails before resolution, its structured missed result records the target; migration does not invent execution metadata. A recovered legacy attempt can safely reconstruct identity only when its original payload explicitly contains experiment, start and model IDs. Otherwise it fails with `legacy_retry_identity_unknown`; the old implicit target or model cannot be established from current time, current promotion or a coincidentally matching date. Submit a new future request rather than claiming recovery of an unknowable publication. The saved `forecast_key` is the canonical UTC identity key; a recovered legacy archive can retain a different original offset-based stored key. Migration leaves those legacy rows unchanged. Explicit inline CLI execution has no durable job record and does not promise recovery across separate invocations.

## Promotion audit and selection preview

`POST /model-promotions` accepts a model ID and a reason of 5–500 characters, validates the model's archived availability and timing metadata, and appends a promotion. Synthetic experiments are rejected. Promotions affect future model resolution only: existing forecasts and jobs with a fully resolved execution retain their saved model. Training does not promote a candidate automatically.

`GET /experiments/{experiment_id}/promotions` returns promotion and model metadata, ordered by creation time and ID descending. Pages default to 25 and are limited to 100; the returned opaque `next_cursor` is supplied as `before` for the next page. `GET /experiments/{experiment_id}/model-selection` previews the same automatic selection policy used by forecast execution for a future `start`, defaulting to 30 minutes after the database check time. It reports the target and cutoff, selected model, promotion identity and reason, or an explicit unavailable result. An incompatible latest promotion remains unavailable rather than silently falling back. The preview rejects synthetic experiments and past targets.

The preview validates archived selection metadata. It does not read model artifact bytes, verify catalogue coverage, reserve a selection, or guarantee eventual publication. A later unresolved job uses the records available at its own selection time; its saved execution provenance remains the authority for the model actually used.

## Timer lifecycle

The worker reconciles on startup and from a dedicated timer every 30 seconds. The timer waits for elapsed time and then reads the current aware UTC clock; it does not replay an in-memory list of cron callbacks. This keeps scheduling active during a long worker job and lets the next tick reconsider current due work after sleep or a wall-clock change. Initial or later failures are logged and retried at the next tick without advancing the decision state. Shutdown stops and joins the timer before releasing the worker's singleton connection.

The former APScheduler configuration used a 60-second misfire grace period. Its [misfire/coalescing documentation](https://apscheduler.readthedocs.io/en/3.x/userguide.html#missed-job-executions-and-coalescing) explains why an overdue callback can be discarded. Inspection of the installed 3.11.3 scheduler also showed that it enumerates missed fire times before coalescing them. The durable planner therefore computes the latest due occurrence directly and keeps recovery independent of callback delivery.

## Due work and catch-up

| Work | JST schedule | Recovery policy |
| --- | --- | --- |
| Recent USGS ingestion | Every 15 minutes | One latest due slot per experiment; retrieve the two days ending at that slot. |
| Daily forecast | 23:40, targeting the next midnight | Queue only while the target is still future. An absent expired target becomes a missed decision. |
| Evaluation | 06:00 | One latest due daily occurrence; evaluate currently completed forecasts against available evidence. |
| Reconciliation | 06:30 | One latest due daily occurrence. For USGS, retrieve the pinned preceding 31 days and then evaluate in the same durable job. JMA uses its imported evidence without automatic network retrieval. |
| Candidate training | Sunday 03:00 | Recover only the latest due weekly occurrence. Pin its requested training endpoint to that occurrence; the model protocol resolves the last completed JST day. Promotion remains explicit. |

Safe work is coalesced to its latest due occurrence, rather than replaying every missed ingestion, evaluation or training callback. Occurrences before an experiment existed are excluded. The canonical due time determines both the logical key and any retrieval/training interval. For example, restarting before 06:30 cannot consume that day's future reconciliation key. A failed USGS reconciliation refresh prevents its evaluation from starting; partial retrieval can still produce explicitly unavailable observations under the normal evaluation rules.

Kind switches apply to whole jobs. Enabling `reconcile` for a USGS experiment still performs its ingestion followed by evaluation even when the standalone `ingest` or `evaluate` kinds are disabled. JMA reconciliation evaluates imported evidence without a network retrieval.

`GET /schedules` lists strictly future regular occurrences in UTC and JST only when the current worker and policy permit applicable work. At exactly 23:40, for example, the next regular forecast occurrence is tomorrow's 23:40; recovery separately identifies the current upcoming midnight as eligible. `recovery.next_check_estimate` is bounded to the next 30 seconds at response time when the worker is verified and process-enabled, including when it is polling a persisted disable. It is an estimate, not a dispatch or publication promise. The eligible target may already have a recorded decision, and queue latency can still cause a missed deadline.

Daily forecast identity remains the experiment plus its canonical UTC target start. Startup at 23:39 creates no upcoming daily job; 23:40 through the instant before midnight can queue it once. An existing job wins any unique-key conflict unchanged, including an existing failed, cancelled or missed decision. Recovery never fabricates an on-time publication or silently retries a deliberately cancelled decision.

## Decision transaction and bounds

Job insertion, scheduler-state advancement, and runtime acknowledgment share one database transaction, serialized by a dedicated advisory lock and protected by the worker ownership fence. A failure rolls back all three, so the next tick can repeat the decision without a false completed watermark. Worker heartbeat updates cannot advance this state. Claim takes the same schedule lock before worker/job control locks so it cannot dispatch newly disallowed work after a configuration change has committed.

Per reconciliation, expired forecast history is limited to 31 target dates, including today's midnight and the preceding 30 midnights. The upcoming midnight is considered separately. A retained truncation record identifies an older interval omitted from individual recovery records; it is not evidence that every date in that interval was a newly missed forecast. Existing records remain intact. Normal ticks preserve the last truncation information.

The planner supports at most 100 real experiments in one automatic decision transaction. Selected IDs filter the SQL query before the limit. All-real scope reads one extra row to detect excess and fails with an actionable error before inserting jobs, advancing state, or acknowledging application. An oversized all-real scope also blocks automatic claims; manual work and terminal-only cleanup remain available. Configuration changes remain available so an operator can disable scheduling or select a bounded scope. Status reports `scope_complete=false`; its capped count is not the full installation count. Inserts use batches of at most 200 jobs. This prevents an unnoticed partial scan from claiming that all experiments were reconciled.

The decision cursor stores the normalized specification hash. A changed active specification resets the catch-up lower bound so newly included experiments or kinds are examined under the same 31-target limit, with omitted older history recorded. A reason-only revision with the same specification does not reset it. Disabled/no-work acknowledgments leave the prior decision hash and cursor untouched; re-enabling an unchanged active specification recovers the elapsed interval since its last successful decision pass.

The maximum reconciled timestamp never moves backwards. The separate observed timestamp records the current clock and bounds elapsed recovery after a backward jump; current and upcoming targets are still reconsidered using their unique keys. Previously recorded decisions are preserved. This is recovery from missed execution, not a guarantee that a misconfigured system clock represents real UTC correctly.

Schedules run only while the worker and computer run. See the [active tracker](remaining-tasks.md) for remaining operational work.
